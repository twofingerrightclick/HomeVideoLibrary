# EF Core catalog migration replacement

Accepted scope: EF Core owns SQLite schema creation and migrations. There are no installations requiring a legacy upgrade path, so the replacement contains exactly one generated `InitialCreate` migration, its designer and model snapshot. Existing raw SQL repository APIs, tolerant reads, durable publication and embedded MKV metadata behavior remain intact. This is not an ORM rewrite.

Storage stays snake_case, with TEXT IDs and date strings matching existing SQL. Preserve unique relative paths, binary normalized `AlbumNames.Key` identity, unique non-null source fingerprints, album/video composite membership keys, reverse membership index and all deletion cascades. Persistence row types stay separate from domain models.

Initialization performs a read-only preflight before mutable database work. Missing or empty databases (including empty EF bookkeeping left before the first migration commits) are allowed; nonempty catalogs without valid EF history and unknown applied migration IDs are rejected with an actionable message. Unsupported catalogs are never deleted, stamped, repaired or recreated. The app must stop before publication recovery or scratch cleanup on rejection. An occupied EF migration lock is rejected without deleting the lock; a linked 30-second initialization cancellation deadline also bounds retries when another tool acquires the lock after preflight. Caller cancellation propagates unchanged, deadline expiry reports an actionable timeout, and an in-flight synchronous SQLite command may delay cancellation observation until its command/busy timeout returns. The deadline trades tolerance for slow storage against an unbounded library-open wait; preserve the database for investigation or create a fresh development library. There is no legacy backup or data repair subsystem. A developer can create a fresh library, but existing album databases must be preserved because albums and memberships are not reconstructible from MKVs.

Use compatible EF SQLite and private Design dependencies plus a pinned local `dotnet-ef` manifest. The design factory requires an explicit absolute scratch database path. Run `MigrateAsync` without a caller transaction. Connections retain foreign keys, `busy_timeout=5000`, pooling disabled and NORMAL synchronization, with FULL/fullfsync for durable publication. Apply journal policy before migration work, then reapply and inspect journal mode after migrations because EF's SQLite creator may enable WAL: local libraries use WAL, network libraries use DELETE on both creation and reopen.

Verification covers one applied history row after fresh and repeated initialization, no pending model differences or migrations, raw SQL album/cache/import compatibility, normalized album uniqueness, relative-path and filtered fingerprint uniqueness, composite keys, foreign keys and cascades, rejection of unknown/newer history and legacy catalogs without altering database/media bytes, fresh/reopened volume journal behavior, cancellation and explicit design paths. Preserve corrupt-row/path/model regression coverage. Run solution build and catalog/album/import/model suites, plus applicable additional suites. Development commands are documented in `DEVELOPMENT.md`.
